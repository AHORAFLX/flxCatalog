# Design before building

What this skill adds is **a wait**: the user sees how the application is going to look, and nothing
gets built until they confirm. Without that wait, this is `/flx-build-product`.

## 0 · Where the original comes from — three roads, all of them first class

An approved original reaches Flexygo by three roads, and **what governs the work is that there IS
one, never which road it came by**:

| The user has… | What happens here |
|---|---|
| **Screens of their own** — screenshots, an HTML, a PDF, a link to something already approved | Take them as the original. Skip steps 4 and 5, file them in step 6 and carry on |
| **A folder generated by Lovable or another generator** | Not this skill: `/flx-lovable` with the path, which also reads its model and its tokens |
| **Nothing yet** | The whole skill, Stitch included |
| **Nothing, and no Stitch either** | The last rung, and it is a real one: the agreed brief plus the platform's own look wearing the client's brand. The end of step 4 carries it in full |

⛔ **The fourth rung is written here so it gets found.** It used to exist only at the end of step 4,
which is reached by somebody who has already been sent off to a supplier that does not answer — so
the road that needs it most was the one that had to stumble into it.

⛔ **And that very fix made the THIRD rung skippable, which is worse — measured 7-Sep-2026.** With
Stitch keyless, an agent diagnosed it perfectly — *«STITCH_API_KEY is missing, exactly as
foreseen»*, which is step 4 word for word — and then offered exactly two ways out: the fourth rung,
or stop. **Setting Stitch up — written in that same step, and a ten-minute job done once — was
never put on the table.** Asked for it explicitly, the agent found it and served it correctly, so
the knowledge is there and reachable: what fails is that it **is not offered by itself**.
⇒ **A silent Stitch is rung 3 first and rung 4 second, in that order, always.** The offer names
both, never rung 4 alone, and «stop» is never one of only two options.

⭐ **And when the project ALREADY has screens built, the palette is read before any of this is
asked.** `/flx-new-development` opens the work and its answer carries the seven skin variables the
application already wears; with those in front of you the question stops being "what colour is your
application?" and becomes "it already uses this: does the new one go the same way?". The ladder
above does not change — same four rungs, same order, for a project from zero and for one that is
running. What changes is the material.

⛔ **Ask which of the three it is before step 4**, and take the answer at face value. Someone who
already has approved screens does not need a design drawn for them — asking Stitch for one produces
a second original, and then there are two things to look like.

⛔ **The screenshots road is not a fallback and not a degradation.** It is how most approved designs
actually arrive: somebody showed the client a demo, the client said yes, and what survives is a
folder of PNGs. From step 6 on, every step is **identical** on the three roads — the palette is
taken off the screen, the technique is chosen per screen, the comparison is answered row by row. If
you find yourself improvising in front of a folder of screenshots, you have left the path, not run
out of it.

⚠️ **First class means the WORK is the same, not that the CHOICE is a coin toss.** Once an original
exists, what governs is that there is one and never which road it came by — that is what this
section is about, and it does not change. But somebody standing in front of the three with none of
them picked is choosing, and there they are ordered: an approved original first when it exists,
Stitch when there is none, the brief last by result. `/flx-context` puts that order in front of the
user before anyone gets here, which is why this step can go on treating the roads as equals.

## 1 · First of all

If the project has no context recorded, `/flx-context` first.

⛔ **And then `flexygo_create_development`, before you reach step 6.** A reference is filed against
a work, so with no active development step 6 refuses — *«There is no active development to file a
reference against»* — and that refusal lands after the user has already handed over their screens.
`flexygo_create_development` itself refuses without recorded context, so the order is fixed:
**context, then development, then the screens.**

Call **`flexygo_inspect_design_brief`**. The project's `DESIGN.md` is what travels to Stitch,
written in the `design.md` standard: YAML front matter carrying the tokens, then the canonical
sections that say how to apply them. Three cases:

- **It does not exist** — ask for the main colour and the typography and write it with
  `flexygo_write_design_brief`. **Do not invent the palette**: if the user has not decided it, leave
  the fields empty and the text itself tells Stitch to choose.
- **It exists but carries no token block** — say so, and write it in with
  `flexygo_write_design_brief`, which puts the block in front and touches nothing else already
  there.
- **It is in the standard** — carry on; if it names a section nobody has decided (the palette,
  most often), that is what is still open, not a defect to fix before moving on.

⛔ **Flexygo's composition grammar is not in `DESIGN.md`, and is never copied there.** Call
**`flexygo_get_design_grammar`** before designing or building any screen: it is what a screen is
assembled from, what each page shape costs, and the hard limits — the design tool does not know any
of it, and `DESIGN.md` describes the look, never the parts.

⛔ **The visual base is OURS, and it is not up for negotiation with the user.** Do not offer to drop
it, and do not ask which style they want: against the same screen and the same model, a generation
with no style brief comes back as a dense 2015-era admin panel — zebra-striped table, cramped rows,
monospaced identifiers — while the same request with our brief comes back as a calm modern product.
Left to itself the tool reaches for "high information density"; the brief is what stops it.

⛔ **LOOK BEFORE YOU WRITE THE IDENTITY, and that is an order change, not a nicety.** This step used
to write the brief before anything had been looked at, which is right for a design that is being
born and wrong for every project that already runs. If the work was opened with
`/flx-new-development`, the seven skin variables came back with it; if it was not, they are the ones
`flexygo_get_module_styling_reference` names, and `flexygo_get_skin_css` says whether the skin also
carries CSS somebody wrote by hand.

**What the palette does NOT decide is whether the new design has to match it** — that is the user's
answer, and `/flx-new-development` section 3 is where it gets asked and recorded. Here it decides
one thing only: **an application that already wears a palette is never asked to invent one.**

⚠️ And the palette is installation-wide, so it is never "just this development": there is one set of
rows per skin and none per origin, and applying a different one repaints every page already built.
Say that before anybody agrees to a free design, not after.

**So there is ONE question, and it is a gate — not a questionnaire.** Ask, in their language,
whether they have anything to say about the design. **If they do not: say the base is ours, write the
brief with no identity — or, in a project that already wears one, with the palette just read — and
move on**; do not walk them through colours and typefaces they have not
asked to choose. **Only if they do**, ask for what they actually have: the colour or corporate
palette, the typeface, the brand, something they want it to resemble — and pass it to
`flexygo_write_design_brief` (`primaryColor`, `palette`, `typography`, `notes`).

The identity **outranks the base**, so an explicit request is honoured even where it contradicts the
house style — that is why it is worth asking for and worth recording with `flexygo_record_decision`.

⛔ **Record it with `affects: development`, and every other decision this skill takes too.** Nothing
decided here settles a task: `affects` validates against the plan, and a palette names no task in it.
Measured 7-Sep-2026, the palette decision was refused three times — `flx-design`, `plan`, and empty —
and ended up only in the chat, which is to say outside `decisions.md`, the one file the later phases
read. It is what makes a decision **come back**; what stays in the chat dies with the session.

## 2 · What they want, and the four questions

Listen to the request. Load `flexygo_get_conventions`, `flexygo_get_entity_anatomy` and
`flexygo_get_schema_and_seeding_guide`, which is the minimum for proposing a model with judgement.

And ask what a screen can never tell you: whether the data is **master, transactional or a mix**;
**which master tables** get created, with the concrete list in front of them; whether example data
is **seeded**; and **which entity is missing**. Every answer to `flexygo_record_decision`.

Before asking anything, `flexygo_recall_decisions`: it may already be answered in an earlier
development, and making them repeat it is wasting their time.

Ask, and record the answers, in the user's language.

## 3 · Propose the model, in text

Entities, which are master and which transactional, the cardinalities, and the menu sections. **This
is not the confirmation yet**: it is working material and it gets corrected in one sentence.

It goes before the design for a measured reason: with the model in front of it Stitch does not
invent functionality; without it, it fills the gap with what an application "should have" of that
kind, and comes back with maps and to-do lists that Flexygo does not paint.

## 4 · Is Stitch there?

**Only if the user has no screens of their own** — third row of step 0. If they have them, the
original already exists: go straight to step 6 and do not draw a second one.

**Check the key in the shell FIRST, because that answer is instantaneous and the call is not.**
One `echo $env:STITCH_API_KEY`, plus one look at whether `.mcp.json` still carries the bare
`${STITCH_API_KEY}`, costs nothing and already separates the two cases below. The client's status
light proves nothing at all: it goes green with the key missing, because the opening handshake asks
for no credential.

**Then call `list_projects`.** It takes a second, and it is the only thing that proves the key
**this window's process** is actually using works — reading the variable proves the key exists, not
that the running process ever read it, and those are different facts.

⛔ **If it does not answer, the FIRST thing you offer is setting it up — «Setting Stitch up, in
full», below — and only then the road without it.** In that order, and both named in the same
breath. The step ends on the fourth rung because somebody has to be able to get there, not because
it is where a silent Stitch lands you: rung 4 is a **choice**, never a fall-through. Concretely,
the question you put to the user has **three** options and not two:

1. **Set Stitch up now** (rung 3 — the recipe below, ten minutes, done once and never again).
2. **Carry on without it** (rung 4 — the agreed brief plus the platform's look with their brand).
3. **Stop here.**

An offer that skips 1 has been measured, and it costs the user a design they could have had.

**And do not stop: there is a way to carry on without Stitch, and this step ends
on it.** Stitch is a supplier, not the flow. But ⛔ **do NOT get there by asking for their own
screens.** Reaching this step means step 0 already asked and they said they had none, so putting
the question again is a loop that ends in "then we stop". Ask for screens here ONLY if something
has changed since — they remembered a folder, a demo turned up — and let them volunteer it.

Separate the two cases instead, because they have different answers:

- **Wired but with no key.** The template already writes Stitch into `.mcp.json`, so the tools are
  present; what is missing is the **API key** in the `X-Goog-Api-Key` header, where the template
  leaves the placeholder `${STITCH_API_KEY}`.

  ⛔ **What you will actually see is `Incompatible auth server: does not support dynamic client
  registration`, and it arrives at ONCE.** With the placeholder unresolved, the client fails
  immediately, not after three minutes. The message you get is the one the trap list below files
  under "do not chase the OAuth" — so it is easy to misread as a different problem entirely. **It
  is not. An immediate `Incompatible auth server` means THIS PROCESS has no usable key**: the call
  gets 401, and the client then tries OAuth discovery and fails there.

  ⛔ **And "no usable key" is TWO different situations wearing ONE message, which is exactly why
  the shell check above comes first.** Either there is no key, or there is one and the running
  process never read it: a key pasted into `.mcp.json` in a window that has not been reloaded
  reaches nothing, because the process was started with the old header. Measured in the field, on
  purpose, before asking for the reload: with the real key already in the file and the window not
  reloaded, the call came back with **the same sentence, word for word**; after the reload
  `list_projects` answered. So somebody who pastes their key, retries and sees the failure of a
  minute ago is **not** looking at a bad key. **Never call a key wrong on the strength of this
  message** — read the variable, reload the window, then retry.

  ⚠️ **The green indicator is real, and there is a mechanism for it**: against the endpoint,
  `initialize` and `tools/list` answer **200 with no credential at all**. Authentication is only
  ever exercised on a `tools/call`. So a healthy-looking client proves nothing — but for that
  reason, not for a slow one.

  **Walk them through it — the recipe is below, it is short, and "get your key" without saying from
  where is not help.**
- **Keyed and still silent.** It is down or slow: offer waiting, or the road below. ⚠️ **Check that
  it really is keyed before you believe this branch.** A key in `~/.claude.json` is not the key the
  session is using: a project whose `.mcp.json` carried the bare `${STITCH_API_KEY}`
  **shadowed a perfectly good global entry of the same name**, and the global
  one never got a look in. Two entries called `stitch` can coexist and the project's wins. If
  Stitch is failing on a freshly created project while it works elsewhere, that is why.

### Setting Stitch up, in full

Give them this, in their language, and offer to wait while they do it:

1. **Generate the key in Stitch itself**: its own Settings has an API-keys section. The key starts
   with `AQ.` and **does not expire**, so this is done once and never again.
2. **Wire it**, either way:
   - `claude mcp add stitch --transport http https://stitch.googleapis.com/mcp --header "X-Goog-Api-Key: <key>" -s user`
     ⚠️ **The header goes LAST and the scope is `-s user`.** `--header` is variadic, so placed before
     the URL it swallows the server name and the URL — the command their documentation shows does not
     work as printed. And a local-scope entry does not show up in `/mcp`.
   - Or paste the key over `${STITCH_API_KEY}` in `.mcp.json`, keeping `"timeout": 600000`.
     **Better still, leave the placeholder and set `STITCH_API_KEY` in the environment**, so a key
     does not end up committed in the project.
3. ⛔ **Then RELOAD THE WINDOW — `Ctrl+Shift+P` → *Developer: Reload Window*. A new chat is NOT
   enough**, and this line used to say it was. Measured 7-Sep-2026: a session opened clean, with the
   real key literally in `.mcp.json`, got **the very same `Incompatible auth server`**. The
   mechanism is that the MCP servers are started by the extension host, **once per window**, so a
   new chat inside the same window reuses the processes that were already running. Only a window
   reload re-reads `.mcp.json` and relaunches them.

   ⚠️ Two different rules, and mixing them is what wasted that afternoon: changing a server's
   **binary** is picked up by killing its process, in the same session; changing **`.mcp.json`** —
   a key, a header, a new server — needs the window reloaded.

   ⛔ **And do not retry before reloading: without the reload you see the SAME error as before
   you pasted the key**, down to the word. That is the one way this recipe gets abandoned a single
   step from working — the failure looks unchanged, so the key looks wrong.

⛔ Three ways to waste an afternoon, worth saying BEFORE they try:

- **A classic Google key (`AIzaSy…`) does not work.** It answers 401 *«API keys are not supported by
  this API»*, by header and by query alike. It has to be a Stitch key, the `AQ.` kind.
  ⛔ **But do NOT use that message to diagnose one.** Against the endpoint, an
  **unresolved `${STITCH_API_KEY}` placeholder returns the very same 401 and the very same
  sentence** (0.31 s), while sending no header at all returns a different one — *«Request is
  missing required authentication credential»* (0.39 s). So "API keys are not supported by this
  API" means *the header carried something that is not a Stitch key*, and a literal `${…}` is the
  commonest something. Check whether the variable is set before telling anybody their key is the
  wrong kind.
- **Do not chase the OAuth it advertises.** Stitch publishes discovery pointing at
  `accounts.google.com`, but Google does not publish a `registration_endpoint`: with no dynamic
  client registration the client refuses with *«Incompatible auth server»*. It would need a
  pre-registered client ID. The API key exists precisely so nobody has to do that dance.
- **Never set the key AND a token.** The SDK's header builder looks at the key first and never falls
  back to the token, so a stale key beats a good token in silence.

**And when there is genuinely nothing — no project, no screens, no Stitch — there is still a way to
build, and it is not building blind.** This is the road `/flx-context` files as
**`origin: briefing`**, and the word is written here on purpose: somebody who reads `briefing` in
`.flexygo/memory/design.md` and comes looking for their road has to be able to find it by that
name. The original is replaced by an agreed brief plus the
platform's own look wearing the client's brand: record the brief with `flexygo_write_design_brief`
and put the brand on the skin's seven variables. A hand-made module is still allowed where the
platform's own fall short — what changes without an original is not whether HTML is permitted but
**what disciplines it**: it answers to the brief instead of to a picture, so what it is for gets
agreed there before it is built.

⛔ **And the row-by-row comparison is NOT run on this road.** There is no original to compare
against, and answering twelve rows about a picture nobody ever drew is theatre. What stays is the
part that still means something: look at the screens, and `flexygo_generate_interface_test_plan` to
click through them, fill them and prove they work. `/flx-build-product` §0 carries the same road in
full. Offer it as a decision with its consequence said out loud: the application will look like
Flexygo with their brand on it, and nobody pretends there was a design to match.

## 5 · Ask for the design

`create_project` → `upload_design_md` with the `DESIGN.md` in base64 →
`create_design_system_from_design_md` (it answers with the `assetId`) → one
`generate_screen_from_text` per screen, and **every one of them with
`designSystem: assets/<assetId>`, `deviceType: DESKTOP` and `modelId: GEMINI_3_8_FLASH`**. Without
`designSystem` Stitch uses a default system and the `DESIGN.md` you just uploaded governs nothing;
without `modelId` you get whatever the default is that week.

⛔ **The model is PINNED here, so it ages — read the enum before you trust this line.** This step
ordered `GEMINI_3_1_PRO`, always and with no alternative, until 9-Sep-2026, and by then the live
schema of `generate_screen_from_text` marked that value **deprecated** in its own words —
*"Gemini 3.1 Pro is deprecated. Use `GEMINI_3_8_FLASH` instead"* — along with `GEMINI_3_PRO` and
`GEMINI_3_FLASH`. Three of the five values the enum offers are dead, and a published skill was
ordering one of them. The day Stitch retires it this step stops working entirely, and the failure
arrives as a parameter error in the middle of a generation somebody is already waiting on.
`GEMINI_3_8_FLASH` and `GEMINI_3_5_FLASH_LITE` are the two alive today.

✅ **The replacement is measured, not assumed.** Six screens generated with `GEMINI_3_8_FLASH` in
one parallel batch on 9-Sep-2026: **six `COMPLETE`, none lost**, inside the time range this step
announces. Nothing in the rest of §5 depended on the deprecated model.

⚠️ **The enum carries its own deprecation flags, and that IS the check.** Before pinning a model,
read the model list off the live schema and take a value it does not mark deprecated. A pinned
model in a shipped skill is a hard instruction with an expiry date nobody is watching; the schema
is the only thing that is.

⛔ **`upload_design_md` wants the WHOLE file as base64 in ONE text parameter, and an agent cannot
put it there. Measured 9-Sep-2026: five attempts, five truncations at 9 %, and the API accepted all
five without a word.** Its schema has `designMdBase64` and `projectId` and nothing else — no file
path, no upload in parts — and its own description says *"Run `base64 -w 0` to get the
base64-encoded string"*, which assumes a console. In an agent session that text has to travel
through the model's own generation, and that is where it breaks: a 24 KB `DESIGN.md` is **33,952
characters** of base64, and what actually arrived was **3,000 of them** — the first chunk — five
times running.

⭐ **It is not a "cannot reproduce long text" failure, and the control is what says so.** That same
base64 was split into twelve 3,000-character chunks, written to twelve files and compared byte for
byte against the original: **all twelve matched, and so did their concatenation**
(`length=33952`). Reproducing one chunk is demonstrably within reach. Assembling them into the
argument of the real call is what did not happen, five times, with the twelve verified chunks
already in front of it.

⛔ **And nothing tells you.** Base64 cut at a multiple of four decodes to valid UTF-8 by accident,
and the tool checks only that it decodes — never that what came out is a whole brief. Those five
attempts left five orphan screen instances in the project, each carrying the brief chopped in the
middle of its first section, and every response looked green.

**So this step has a precondition, and it is said out loud instead of assumed:** producing
`designMdBase64` needs a **real shell** — `base64 -w 0 DESIGN.md` run as a command, its output
handed straight to the call — and not the agent's own generation. Two roads when there is no shell:

- **Read back what actually arrived.** After the first `generate_screen_from_text` the project
  theme is written in full from the asset (check (d) below): fetch
  `get_project().designTheme.designMd` and look in it for the brand name, the palette hexes and the
  type scale. A brief that arrived at 9 % carries the opening section and nothing after it. **Never
  file a design system you have not read back.**
- **Or leave the base64 road altogether** and build the design system from explicit tokens with
  `create_design_system`, section 5-bis. That is the road the 9-Sep-2026 pass took after abandoning
  this one, and it generated six screens. What it costs is the prose half of the brief, which makes
  the composition line below matter more and not less.

**Never carry on as if the upload had worked.** A truncated brief does not fail: it produces screens
that look plausible and match nothing that was agreed.

⛔ **`upload_design_md` still DISTILS the brief — and since `DESIGN.md` moved to the `design.md`
standard, that distillation is measured again, and it changed.** Measured 9-Sep-2026: the standard
form of the brief is **4,014 characters**, against the old prose's 24,942, and it uploads without
fighting the base64 limit at all. The one the server ships since 10-Sep-2026 is **3,931**: the
same prose with every rule addressed to the AGENT taken out — "gets regenerated, not shown", the
measured ⛔ paragraphs, the WCAG figures — because an A/B on the same screen showed those buy
nothing from Stitch, while the DESCRIPTIVE half ("not an admin panel, do not optimise for
density") is what keeps a screen calm: the brief without it came back cramped, in capitals, and in
a serif fallback. And a ninth section, **`## Project identity`**, that is ours and not the
standard's: measured the same day, it travelled verbatim on web and on mobile and everything it
named landed on the screen — an accent, a warm page where the prose asks for a cool one, IBM Plex
Sans, square corners against 8px tokens, the brand mark. It is where the user's decisions go, and
`flexygo_write_design_brief` is what writes it. Its `typography` and `spacing` tokens arrive **literal**, one
value for one value, under the same names — `page-title 30px/700`, `spacing.margin: 32px`, and the
rest of the scale — where the old prose form let the tool guess them. See
docs/plans/2026-09-09-design-md-que-parte-merece-subirse.md.

✅ **And the composition vocabulary survives when it is written where the standard has a box for
it: `## Components`.** The body this server ships puts the list-screen shape there, and the design
system Stitch derives from it echoed it back in its own `Components` section, close to verbatim:
*"Features an integrated filter row, search input, clear pager, and an accessible per-row action
menu. Dates must be formatted relatively."* That is the exact vocabulary that used to fall to zero
— `pager`, `filter`, `search`, `per-row action menu`, `relative date` — when it lived in prose the
old form had no slot for.

⛔ **Put this line in the prompt of every LIST screen anyway — it is a SECOND channel now, not the
only one.** `Components` carries the shape of the box; it does not replace naming it again where
the generation is actually asked for, and the measurement below is what the line alone still buys.

✅ **The screen prompt is the one channel that does not pass through the distillation, and it
works.** Measured 7-Sep-2026 with a control, in the same project and on the same design system:
two generations of one list screen whose only difference was this line. Without it — no pager, no
search, no filter row, no actions column, and column headings in capitals the design system itself
forbids. With it, every one of them, dates in the user's own format, and the palette and the
semantic status pills still ours.

> Inside the box of a list screen: a row of filters with a real date-range control in the user's
> date format, a global search in the header of the box, a pager at the foot saying how many
> records of the total are shown, an actions column with its own heading and a per-row menu, and
> relative dates for the recent ones.

**And two more words on the same line, measured 10-Sep-2026 to be the prompt's to say and not
the brief's:** *column headings in sentence case, and the code column on one line.* Four briefs on
the same list prompt: of the three that left the capitals rule to the brief, two came back with
every column heading in capitals, and the code column wrapped on three of the four — including the one
whose brief forbade both. The prompt is the one channel that does not pass through the distillation.

**Say that, and stop.** The temptation is to keep adding constraints, and a prompt that prescribes
everything is how a record card came back with no chrome at all. The design system carries the
style, this line carries the composition, and what is left is what Stitch is for.

⚠️ **The line is for the WEB list screens only.** The offline app is painted by Ionic in its four
screen shapes and carries none of those controls; what it needs from the brief is the visual
identity, which is the half that survives the distillation whole. Do not add it to a `MOBILE`
prompt. **What a `MOBILE` prompt does need is its own three words: *section headings in sentence
case*.** Measured 10-Sep-2026 on five mobile generations from four briefs, two of which forbade
capitals outright: every one of the five drew its list heading in letter-spaced capitals. The
brief does not reach that; the prompt does.

⭐ **And this is why the brief still travels even though half of it does not.** What it buys is not
one generation: it is that the palette and the identity are the PROJECT's, written down and read
back, so the next development on the same product does not invent a look of its own. The one thing
the brief-less road did better — status colours that mean something rather than a ramp of one hue —
comes from here.

⛔ **This batch is the WEB screens, and the offline app's are NOT in it — whatever the context gate
answered.** This step used to say the opposite: that an app answered "now" got its `MOBILE` screens
asked for here, in the same batch, because they were wanted within days. It contradicted the rule
two steps earlier that the app is a **second development** — the whole point of which is not
carrying both halves at once — and drawing its screens with the web ones carries them at once by
another door. Say plainly that the mobile screens are not being drawn yet, and where they will be:
section **5-ter**, below, in the app's own phase.

**How many screens: derived from the model of step 3, never a fixed number.** The dashboard, the
list and the record card of the main entity, and one more —list or card, whichever the flow
needs— per additional principal entity, up to **six**. Say the cost before starting: **one to three
minutes per screen**, so four entities are ten to fifteen minutes before the user sees
anything. If they would rather see three first, do three and offer the rest afterwards.

✅ **Launch the whole batch in PARALLEL — all the calls in one turn, not one after another.**
Five `generate_screen_from_text` in a single turn come back **5 of 5 complete**,
five distinct `sessionId`, five distinct `name`, none lost and no timeout (with `"timeout": 600000`
in place, which is a precondition either way). Nine in a single turn come back **9 of 9 complete
in 15 min 43 s of wall clock**, none lost. The wall clock of a batch is its slowest screen, not the
sum of them.

**Write down the wall clock of the BATCH — when you sent it and when the last response landed — and
nothing finer.** A per-call timestamp is not obtainable from this client and asking for one only
produces an invented number: `generate_screen_from_text` returns no date, **`get_screen` does not
return `createTime` either** (it answers `deviceType`, `height`, `htmlCode`,
`name`, `screenshot`, `title`, `width`, and nothing else), and in a parallel turn every response
arrives at once anyway. The batch wall clock is the whole of what can be measured, and it is enough
to say what the parallel saves.

**The prompt, per screen shape, always in this order:** the shape (list / record card / dashboard,
in the words of the three page shapes of `DESIGN.md`), the chrome named explicitly —the left
navigation column and the slim top bar— on EVERY screen, the entity and its fields from step 3 with
sample data in the user's language, the navigation entries the model gives and no others, the one
primary action, and the status values with their colours. Stitch rewrites every prompt it receives;
a vague one comes back with maps and to-do lists — a record card asked
without naming the chrome comes back with none at all while the list screen of the same project has
it.

**What the API can and cannot see, and it is the trap that cost a
whole afternoon once:** Stitch answers in ONE response after 73–174 s, and a client with no
`timeout` on the `stitch` server gives up at about a minute —«The operation timed out»— while
Google keeps working. One run that regenerated on every timeout ended with **eleven
screens for the three it asked for**. And the screen a generation makes is reachable through the
API **only by the `name` that same response returns**: `list_screens` and
`get_project().screenInstances` do not list it — not after ten hours — because instances are canvas
placements the Stitch UI creates when somebody opens the project, not something the API writes. So:

1. **`"timeout": 600000` on the `stitch` entry of the client's `.mcp.json` is a precondition, not
   an optimisation.** With it the response arrived complete at 121 s with the screen inside;
   without it the same call is lost at 60 s. If the entry has no `timeout`, say so and stop before
   generating.
⛔ **The screenshot URL serves a THUMBNAIL unless you ask for the full size.**
The `screenshot.downloadUrl` fetched as it comes back gives **512 px wide, 47 KB**; the same URL
with **`=s0`** appended gives the real screen — **2560×2520, 255 KB**. `get_screen` reports the true
`width`/`height`, so compare what you downloaded against them and re-fetch if it is smaller. A whole
run was filed at 512 px and the person who had to approve the design could not read the labels. Do
not confuse it either with `get_project`'s `thumbnailScreenshot`, which is the project's cover.

2. **When the response arrives, keep what it carries, immediately**:
   `outputComponents[…].design.screens[0]` has the screen's `name`, `htmlCode.downloadUrl` and
   `screenshot.downloadUrl`. Download both files now — the URLs **expire** — and read the screen
   back with `get_screen` on that `name` (one retry on "service is currently unavailable"; it is
   transient). The list of `name`s you kept IS the inventory of what was generated; nothing else is.

   ⚠️ **And `outputComponents` is not only the screen — read the rest of it.** The tool's own
   contract says that when it carries **text**, that text is for the user, and when it carries
   **suggestions** ("Yes, make them all"), those are offered to the user and an accepted one is
   passed straight back as the next `prompt`. Reading only the screen out of
   that envelope drops everything else unopened, so whatever Stitch is saying about what it
   just drew never reaches anybody. Report the text; offer the suggestions; never act on one
   without the user choosing it.
3. **If a response is still lost** (a timeout with the `timeout` in place, a connection cut): do
   NOT generate again on reflex, and **do not conclude the screen is gone — there is a recovery
   route and it costs nothing.** `get_project` says whether the screen was made (`updateTime` moves
   and `thumbnailScreenshot` changes to the new one). Ask the user to **open the project in the
   Stitch web UI**: that is what creates the canvas instances, and once they exist
   `get_project().screenInstances` hands back **every** screen id, lost ones included. On a
   9-screen run whose responses were long gone, once the project had been opened,
   `get_project` returned every instance of the run, and `get_screen` on those ids worked normally.
   Only if the user will not or cannot open it do you generate that screen again — and only then
   does it count against the budget.
4. **Budget: three attempts per screen**, lost responses included. After that, stop and say which
   screens are missing. Do not keep going.

⛔ **NEVER count an attempt, and never call a correction done, from the TEXT of the response. Fetch
the content again and compare it.** Stitch describes changes it has not made, and it does it with a
straight face — measured twice on 7-Sep-2026, independently, both times by comparing bytes and not
by reading prose:

- **`generate_variants` ×4**, directed with `aspects` and `creativeRange: REFINE` to fix four
  screens. All four responses carried `sessionEvent.dom_operations` **describing the corrections**.
  `get_screen` straight afterwards: **the four files unchanged, byte for byte.**
- **`generate_screen_from_text`**, an extremely prescriptive prompt naming the two previous
  failures. It returned **a NEW screen id with the SAME md5** as the attempt before, and prose
  saying the opposite.

So, after **every** `generate_screen_from_text`, `generate_variants` or `edit_screens`:

1. `get_screen` on the id it hands back, and download the HTML again.
2. **Hash it** and compare with the hash of what you had before the call.
3. **Same hash ⇒ nothing happened.** Say so, do not report the change the answer described, and
   ⇒ **it still costs an attempt** — the budget counts calls made, not screens moved. What it does
   not buy you is a repeat of the same prompt: an identical call after an identical result is the
   third attempt spent on an experiment already run. Change the tactic or stop.
4. Only a **different** hash lets you say the correction was applied — and then it goes back through
   the four checks, because a real change can break what it did not touch.

⚠️ A new screen **id** is not evidence of a new screen: the second measurement above got one, with
the same bytes inside. The id is the supplier's bookkeeping; the hash is the artifact.

Two more things that save you the stumble: **errors arrive with HTTP 200**
(`upload_design_md` failed one time in two with "service is currently unavailable" — **retry**
before calling it broken), and `list_screens` returning zero screens after generating is not a
failure — see above, it never lists them.

⛔ **Look at each screen before filing it: a generation can come back EMPTY and still succeed.**
Of five screens, one came back as the shell (rail, title, primary button) with
an empty card in the middle carrying the literal text **"Rendered correctly"**: no table, no rows, no
data. It was filed as the approved reference and reported on as if it had content. Two checks, both
cheap:

- **Read the HTML you downloaded.** No rows, no fields, or a placeholder string like "Rendered
  correctly" means the generation failed however green the response looked.
- **Compare the file sizes across the set.** The empty one was 15 KB against 43–53 KB for its
  siblings — the smallest of the batch, and that was visible before anyone opened it.

A screen that comes back empty is a **real failure and counts against the budget**: regenerate that
one screen, and if it comes back empty again, say so and stop. Never file it.

⛔ **Before showing anything, review every screen and correct only what is Stitch's error.** Four
checks per screen, and the third one is done with your eyes on the image, not on the markup:

- **(a) The size.** The downloaded screenshot measures what `get_screen` declares — `=s0`, above.
- **(b) The markup.** The HTML has rows or fields and no filler: no "Rendered correctly", no empty
  card where the data goes, no size that is the outlier of the batch.

  ⚠️ **A chart passes (b) and still draws nothing, so (b) never clears a chart.**
  A dashboard came back carrying `<svg>` and two `<polyline>` of eight points each whose
  values matched both series exactly — and an empty plot box, because SVG `points` does not accept
  percentages and that attribute was written entirely in them. The data was in the markup and not in
  the pixels. Only (c) catches this one.
- **(c) LOOK at the screenshot.** Nothing cut off by the edge of the frame, no cell truncated with an
  ellipsis or wrapped over several lines, no overlapping text, no empty corridor between the rail and
  the content, no text in another language, no chart without an axis and a legend, **and the case not
  forced in either direction** — no header, KPI label or field label in capitals, and no proper noun
  flattened to lower case ("cinta transportadora a", "laura m.").

  ⚠️ **`grep uppercase` over the HTML gives false positives, so read the class, do not count it.**
  One screen returned **19 hits for `uppercase` and every one of them was
  `lowercase first-letter:uppercase`** — which is the lower-case defect, not the capitals one. Both
  fail check (c); what changes is which of the two you are looking at, and only the surrounding class
  says. The reliable read is the screenshot.

  ⛔ **Expect the capitals defect and check for it every time: the brief does not prevent it.**
  On a clean project, a faithful theme and the newest grammar, first attempt:
  **7 of 7 `<th>` came back `uppercase tracking-wider`** — while the design system Stitch itself had
  just derived from that same brief stated, in its own words, *"Sentence Case Only:
  `text-transform: none` is strictly enforced"*. It restates the rule and breaks it in the same
  response. Writing the rule harder is therefore not the fix; catching it is. (The lower-case half
  held in that same run — "Carlos Ruiz" and `VAC-2024-001` both kept the capitals they own — and so
  did the cells: `truncate` at 0.)

  ⚠️ **It is intermittent, not certain, so it is checked and never assumed in either direction.**
  Over nine dashboard screens in a different clean project on the same grammar:
  **zero** `uppercase`, zero `tracking-wider` and zero forced lower case, on the first attempt and
  after every retry. One clean project gave 7 of 7 and another gave 0 of 9. The check costs nothing
  and the defect is a coin toss.
- **(d) The design system — and the FIRST half of this check is your eyes, not a field.**

  ⛔ **`designSystem.name` does NOT detect an identity drift, and reading it as though it did is
  what gives false calm.** Measured 9-Sep-2026, **twice in the same pass**: one list screen came
  back with another logo, a header naming a different product, a full-width search bar outside the
  list box and an **English** placeholder in a Spanish application; and one regenerated dashboard
  came back with a different shell altogether, inventing menu entries and a footer. **In both cases
  the response named the same design system as the correct screens** — in the second, literally the
  same `assets/…` id. The field this check used to point at said nothing, both times. Two drifts
  over seven generations: not a freak screen, a real rate on **every** generation, with a variant
  or without one.

  **So compare the SHELL of each screenshot against the shell of the others**, explicitly and item
  by item: the brand mark, the wording of the header, where the search sits and what shape it has,
  the navigation entries and the footer, and the language of every placeholder. A screen whose
  chrome does not match its siblings has drifted, whatever the response says. It is corrected like
  any other execution error — `generate_variants` with `aspects: [LAYOUT, COLOR_SCHEME,
  TEXT_CONTENT]` and `creativeRange: REFINE` put the first case right at the first attempt — and
  the fix is confirmed by looking at the new screenshot, never by reading the id back.

  **`designSystem.name` still gets read, for the one thing it CAN catch**: Stitch sometimes builds
  a NEW system out of the style paragraph and answers with that one instead — non-deterministic, in
  parallel and in sequence, and it silently changes what the screen is being compared against. A
  name that changed is a real finding. A name that did not change is evidence of nothing.

  ⛔ **And `get_project().designTheme`, a THIRD thing, which nobody was looking at either.**
  The project carries a theme of its own. **Generation writes it** — walking
  a fresh project one call at a time shows it: empty at `create_project`, still empty after
  `upload_design_md`, still empty after `create_design_system_from_design_md`, and **written in full
  by the first `generate_screen_from_text`**, derived from the asset that call was given.

  ⛔ **What the theme keeps of the brief is NOT predictable in form, and this passage used to say
  "verbatim".** Measured 10-Sep-2026 over seven generations in fresh projects
  (docs/evidencias/2026-09-10-design-ab): the brief's body came back **verbatim** three times,
  **rewritten** by Stitch into its own seven headings twice, and **dropped entirely** — only the
  front matter left — twice, one of them the longest brief of the set. What held all seven times:
  the `typography` and `spacing` tokens, one value for one value, and the seven-heading
  `styleGuidelines`. So read the theme for the TOKENS and the palette, and never conclude from a
  body that is missing or reworded that the upload failed — check the tokens, and check the screen.

  ⚠️ **The danger is a REUSED project, not the mechanism.** A project accumulates: the one from
  the nine-screen run carried **ten** design-system instances and a project theme arguing for
  "Information Density: High", "alternating row stripes (Zebra striping)" and a 280px sidebar —
  every one a thing the brief forbids in as many words — left behind by an earlier arm that had
  deliberately measured a dense variant. The response-level check was green for all 21 generations
  while that sat underneath. So: **one project per design effort, never a project reused across
  experiments or across clients**, and **read `get_project().designTheme.designMd`
  before you read the screens** — so a contaminated project is caught before the generations get
  blamed for it.

If any of the four fails it is an execution error and not a matter of taste: **correct that screen
without asking and without showing the bad one**. It counts against the budget of three; at the third
attempt, say which screen is missing and stop.

⚠️ **And "correct" is not always "generate it again from scratch." When what failed is
composition, the retry has to be a DIRECTED one:** `generate_variants` on that screen's id, with
`variantOptions.aspects` naming what is wrong — `LAYOUT`, `COLOR_SCHEME`, `IMAGES`, `TEXT_FONT`,
`TEXT_CONTENT` — `creativeRange: REFINE` (the default is `EXPLORE`, which is not what you want when
the screen is nearly right) and `variantCount` 1–5. It is the same five aspects Stitch's own
Generate ▸ Variations menu offers, plus a creative range the menu does not expose.

On a dashboard whose only defect was a clipped title: `aspects: [LAYOUT]`,
`creativeRange: REFINE`, `variantCount: 2` — **both variants fixed the title and touched nothing
else**; the two charts kept their axes, their legends and their data, the table stayed whole, and
`truncate` fell to 0 in the markup of both. In the same session a blind re-roll of that same shape
failed **9 times out of 9**. So:

- **A composition defect — something clipped, overlapping, out of its box, a broken cell, a case
  forced the wrong way — goes to `generate_variants` first**, and the blind re-roll is what you do
  after it, not instead of it.
- ⚠️ **A content defect goes to `aspects: [TEXT_CONTENT]`.**
  On a list screen
  whose rail footer said **"Sign-out"** on an otherwise all-Spanish screen —
  `aspects: [TEXT_CONTENT]`, `creativeRange: REFINE`,
  `variantCount: 2`, the defect named in the prompt: the diff against the original is **ONE line**,
  `Sign-out` replaced by the correct Spanish label in sentence case, out of 25,763 bytes.
  Nothing else moved — the five rows, the codes,
  the proper nouns, the dates, the pager and every class identical, and the 7 `uppercase` table
  headers survived untouched, which is the aspect staying in its lane. So: **the wrong language, a
  wrong label, an invented figure in a cell — name it and vary `TEXT_CONTENT`.**

  A fresh generation is for what was never drawn at all — **except that a chart which came back
  empty is NOT one of those.** On a
  dashboard whose donut was a bare grey ring: `aspects: [LAYOUT]`, `creativeRange: REFINE`,
  `variantCount: 1`, with the four figures and the total named in the prompt — the variant drew the
  four proportional segments, and the same call had already redrawn that screen's empty line chart
  from the series written into the prompt. **Name the drawing that is missing and its numbers, and
  vary `LAYOUT` first.** Keep the fresh generation for a section that is not on the screen at all.
- ⛔ **Two things worth knowing about that call, and both cost you if you do not know them.** First,
  **`variantCount: 2` can come back as two screen ids whose HTML is byte-identical** — same md5, one
  screenshot file between the two — while the response prose claims variant 2 carries "a
  millimetric adjustment to the footer alignment" (its words, translated). It did not. **That
  happens sometimes and not always**: the same call can instead give back two variants with
  different md5s, 126 differing lines and two different mechanisms for the one fix, and both pass
  the review. Which of the two you were handed is knowable only from the bytes. **Diff the files; never report a difference
  because the answer described one.** Second, the response **can fail to fit**: at 63,563 characters, over
  this client's cap, it spills whole to a file under `tool-results/`. That is not a failure and no
  screen is lost — but step 2 above cannot be done off the preview, so read the envelope out of
  that file.
- ⛔ **A variant is a NEW screen, so it goes back through the four checks — it can fix what you
  named and break something you did not.** A `[LAYOUT]` variant asked to draw
  two empty charts and to stop the cells wrapping did draw the lines, and pushed the whole page past
  its right edge — a KPI tile, the primary button, the last week of the x-axis and the last two
  table columns all cut off, none of them wrong before the call. A second directed variant naming
  the overflow fixed both, at the cost of that screen's last attempt. The runs above where a variant
  "touched nothing else" are real and they are not a guarantee. And the prose keeps overstating: a
  third variant answered that it had made the page taller so the table would fit whole, and the
  declared height was the same 2,048 before and after while the table went from five rows to four.
- **Each variant call counts as one attempt against the budget of three**, like any other retry.
- ⛔ **And a variant can move NOTHING at all while the answer says it did** — four in a row, measured
  7-Sep-2026, `dom_operations` describing corrections that were never written. Hash the screen again
  and compare it with the one you had before the call, exactly as §5 point 4 demands. Same hash ⇒ no
  correction happened, whatever `dom_operations` narrates.

**Only what passes the review reaches the report, and that is where the user's judgement begins** —
taste, composition and content, never breakages. Over eleven screens, this
review would have let six through and regenerated five on its own, with nobody having to look at a
broken one.

## 5-ter · The offline app's design, in its OWN phase

⛔ **This section runs when the APP's development is opened, not while the web one is being drawn.**
The app is a second development — `/flx-context` says why, and `flexygo_create_development` refuses
a second unfinished one, so the shape is fixed: the online work closes, reviewed and verified, and
then the app opens with its own slug, its own original and its own approval.

⚠️ **It is not a smaller version of the web design and it is not the web screens narrowed.** The app
is painted by Ionic in screen shapes the web pages do not have, so a design that only covers the web
leaves the mobile part to be designed later, badly, and paid for twice. That is why it gets a phase
rather than an afterthought.

### The same three ways, in the same order, asked again for this surface

The offline original is a DIFFERENT original, so the question is put again — and what was answered
months ago about the web half does not settle it:

1. ⭐ **There already is an approved mobile original** — a mobile design of their own, or the mobile
   sections of the generated project `/flx-context` asked them to name. **The best road when it
   exists**, for the same reason as on the web: it is what was already approved.
2. **There is none, and Stitch draws it now** — the one to recommend when there is nothing, because
   it is the only one of the three that ends with something the user can look at and approve.
3. **There is none and Stitch is not wanted** — the brief plus the platform's own look. Last by
   result, and a real road the user may choose.

⛔ **Then file it: `flexygo_record_design_origin(surface: 'offline', origin: 'stitch', pointer: 'stitch project 42, design system assets/7')`.**
Its own entry, beside the web one, in `.flexygo/memory/design.md`. `flexygo_recall_decisions` brings
both back, which is what lets this phase see what the web half was built from instead of inventing a
second look for one product.

### Which mobile screens, and how they are generated

Which ones to ask for is not yours to guess:

- **When the original is a generated project or a folder of screens**, `/flx-context` already asked
  the user WHICH SECTIONS are the offline app. Draw those and no others.
- **When there is no such original**, there is nothing to carve up: derive them the same way as the
  web ones, from the model, and say which you are drawing before you start.

⭐ **Give the offline app a design system of ITS OWN, from the same brief.** A second
`create_design_system_from_design_md` over the same `DESIGN.md`, this one with
**`deviceType: MOBILE`**, and its own `assetId` for the mobile generations. The identity stays the
same product's — that is the whole point of deriving both from one brief — and only the frame
changes. Name that frame in the mobile prompts: **the app is Ionic**, so its screens are Ionic's
own shapes, with the platform header, the bottom tabs and its cards, never a desktop layout made
narrow.
⚠️ **Name it in the PROMPT, not in the brief — measured 10-Sep-2026.** Two mobile briefs carried
"the application is built with Ionic, so the header, the toolbar and the back button are Ionic's
own"; neither design system kept a word of it — both wrote "native mobile toolbar structures" —
and the screens were indistinguishable from the one whose brief never mentioned it. The same
brief serves both surfaces; the mobile design system is the `deviceType: MOBILE` derivation of it,
measured that day to differ from the desktop one in its `Components` (list rows, KPI tiles) while
keeping the same tokens and palette.

Everything else in this file applies unchanged: the batch in parallel, the review before showing
anything, filing the original in step 6, the wait in step 7 and the row-by-row comparison in step 9.
What does NOT apply is the composition line of step 5 — it is for web list screens only.

## 5-bis · The rest of Stitch's surface, and what it is NOT

Stitch serves **15 tools**. §5 uses six of them, §7 a seventh, and the rest were being left on the
table because nothing here named them. Off the live schemas:

- **`generate_variants`** — the directed retry, above. Use it before a blind re-roll.
- **`apply_design_system`** — re-skins screens that **already exist**, without regenerating them.

  **It does NOT need a canvas instance.** On a project whose only
  `screenInstance` was the uploaded `DESIGN.md` file, passing the **screen's own id** as `id` and
  its resource name as `sourceScreen` was accepted and worked, twice. So
  `{id: <screenId>, sourceScreen: projects/<p>/screens/<screenId>}` is the call, and `get_project`
  is not a precondition.

  **And it re-writes the TOKENS, never the screen's classes** — which decides what it can and
  cannot do for you, so read this before offering it as "the same screens, another colour":
  - Applying the **same** asset gives back a new screen id whose HTML is **byte-identical** to the
    source. Idempotent, and the proof it really re-rendered the right screen.
  - Applying a deliberately different one — `colorMode: DARK`, `customColor`/`overridePrimaryColor`
    `#EA580C`, `overrideSecondaryColor` `#F59E0B`, `roundness: ROUND_FULL`, `SPACE_GROTESK` —
    changed 160 lines and landed **the fonts and the roundness** (the config's `borderRadius` went
    to 1/2/3rem, the nav entry and the button became pills) and **nothing else the eye could see**.
    The page stayed light, the primary button stayed blue.
  - Why, exactly: **a token the markup does not reference changes nothing.** `primary` did take
    `#EA580C` — and the screen paints its one primary action with `bg-secondary` (3 uses;
    `bg-primary`, 0), and `secondary` kept `#0058be` although `overrideSecondaryColor` was passed.
    `colorMode: DARK` arrived as the bare class `dark` on one element with no dark palette behind
    it, over a `page-bg` still `#F8FAFC`.
  - **It merges, it does not replace.** The levels the new system did not declare kept the old
    system's values — five of the ten `fontFamily` levels stayed Geist while the other five became
    Space Grotesk.

  So it is genuinely the cheap road for **shape and type** and for an accent the markup actually
  uses; it is **not** a way to turn a light design dark, and a colour swap has to be checked in the
  downloaded HTML rather than assumed. The response also carries the **original `prompt`** of the
  source screen, which is the only place that text is recoverable once the generation response is
  gone. A full regeneration remains the expensive road, and it throws away everything already right.
- **`list_design_systems`** — with `projectId` **empty** it lists the GLOBAL assets, the ones not
  tied to a project. That is the same emptiness `create_design_system` uses to create one.
- **`delete_project`** — there is a tool for the tidy-up, and its own description demands the user
  say so explicitly. Never on your own initiative.
- **Two parameters §5 fixes without saying they are choices**: `deviceType` also takes `TABLET` and
  `AGNOSTIC` besides `MOBILE`/`DESKTOP`, and `modelId` takes five values of which the live schema
  marks **three deprecated** — `GEMINI_3_PRO`, `GEMINI_3_FLASH` and `GEMINI_3_1_PRO`, that last one
  being what §5 ordered until 9-Sep-2026. The two alive are `GEMINI_3_8_FLASH` and
  `GEMINI_3_5_FLASH_LITE`. `DESKTOP` + `GEMINI_3_8_FLASH` stay the default — that is the
  combination the rest of this skill relies on; Flash-Lite is there for a cheap exploratory pass
  before the real one, if you want it. Read the enum before pinning either: it is the only place
  that says which values are dying.

⚠️ **`create_design_system` / `update_design_system` take HARD TOKENS, and that is not the road
here — yet.** The `theme` accepts `headlineFont`/`bodyFont`/`labelFont` off an enum of 68 faces
(Geist, IBM Plex Sans and JetBrains Mono among them), `colorMode`, `colorVariant` (10 of them),
`customColor` with `overridePrimary/Secondary/Tertiary/NeutralColor`, `roundness`, and **`spacing`
and `typography` maps** carrying `fontSize`/`fontWeight`/`lineHeight`/`letterSpacing` per level —
the very scale that today travels as prose inside the `DESIGN.md`, and prose is what this month's
measurements keep watching the generator disobey. It also takes `designMd`, so tokens would be
**added to** the brief, not swap it. Two reasons it is not the road today, and both have to be
answered before it becomes one:

1. **It is unverified where it counts.** The `upload_design_md` →
   `create_design_system_from_design_md` road answers with the asset that was passed in
   **21 generations out of 21**, and swapping the only leg that has never failed for one
   nobody has run is how a good pass becomes an unexplainable one. What has been exercised is only the
   creation: `create_design_system` with a bare token theme and no `designMd` returns an `assets/…`
   id and echoes the theme back **exactly as sent, with nothing derived** — no `namedColors`, no
   expanded palette, unlike the `designMd` road which comes back with the whole palette extracted.
   This paragraph used to end «No screen has ever been GENERATED from a token-built system; the
   only thing one has been used for is the re-skin above, where half of what it declared did not
   reach the pixels» — and on 9-Sep-2026 that stopped being true. With `upload_design_md`
   impossible to complete without a real shell (§5), the pass built the system with
   `create_design_system` and explicit tokens and **generated from it: six screens, six
   `COMPLETE`**. One pass is not twenty-one, so this stays the second road and not the default;
   what it is no longer is unexercised, and it is where §5 sends you when there is no shell to make
   the base64 with.
2. **A GLOBAL asset (`projectId` empty) can only ever carry the house style, never the project.**
   `DESIGN.md` is two halves too, just not the same two any more — the front matter, which is this
   project's **identity** and by §1 **outranks** everything else, and the canonical body, which is
   the house style the server ships and is the same everywhere. (Flexygo's composition grammar sits
   outside `DESIGN.md` entirely now — §1 above.) A "Flexygo 2026" global asset is therefore right
   for a project that declared no identity (the common case of §1) and wrong for one that did,
   because reusing it silently drops the half that wins. If it is built, it is built for the first
   case and named so nobody reaches for it in the second.

**Three smaller things the parameter census turned up**, none of them worth a paragraph on its own:
`create_design_system_from_design_md` also takes `deviceType`, which nothing passed until §5 began
using it for the offline app's own system — what it changes is still unmeasured; `list_projects`
takes a `filter` that defaults to `view=owned`, so **projects shared with the user are invisible**
unless you ask for `view=shared`; and on `get_screen` the `projectId`/`screenId` pair is marked
**deprecated** in favour of `name`, which is what §5 already uses. And `update_design_system` wants
the WHOLE `designSystem` back, not a patch: it replaces, so every field has to be re-sent.

**What Stitch does NOT have**, said here so nobody spends an afternoon looking: no export or
download of a project, no reading of comments, nothing behind the web menu's "Show QR / Export /
Download", and no dates anywhere — `get_screen` returns no `createTime`.

## 6 · File it now

File every approved screen with `flexygo_record_reference` — the screenshot, and then the HTML when
there is one, as a SECOND call for the same screen. **Now, not at the end**, whichever of the three
roads it came by: Stitch's URLs **expire**, a link the user pasted goes down, and a folder of
screenshots gets tidied away. With no reference there is no comparison, only opinions.

**Archiving the HTML is not bookkeeping: it is what the comparison is allowed to demand.** On a
screen whose markup is on disk, `typography` and `spacing` aim at **almost identical** like the
other ten rows, instead of at *recognisable* against a PNG — a `font-family` cannot be read off an
image and a padding measured on one has no known render scale. It is per screen: archive it for six
screens and it is raised on six, for two and it is raised on two. The tool refuses the `.html`
before that screen's capture is filed — the source is archived alongside the screenshot, never
instead of it.

**And file the ones that are going to be built.** Walk the list and check that each screen heading
for Flexygo has its own reference: filing the two screens nobody was going to implant, and none of
the twelve that were, is a failure that has already happened.

⭐ **File the design system too, not only the screens.** `create_design_system_from_design_md`
answers with an `assetId`, and that id is this product's look made reusable: a later development
generates with the SAME system — `generate_screen_from_text(designSystem: assets/<id>)`, or
`apply_design_system` over screens that already exist — instead of deriving a fresh one and
drifting away from what the client already approved. Record it with `flexygo_record_decision`
(`affects: development`), naming the Stitch project id, the desktop `assetId` and, when there is
one, the offline `assetId`. That is a project fact and `flexygo_recall_decisions` is what hands it
back months later; the `DESIGN.md` at the root is the source it was derived from, and
`flexygo_get_design_grammar` is where the composition rules that source does not carry live.

## 7 · Show them and wait

⛔ **"Show them the screenshots" does not happen by saying you have them.** In a terminal the user
sees your text and nothing else, so asking "do you approve the design?" over a filename is asking
them to approve something they cannot see, and it is the gate this whole skill
exists for. **Publish a report as an artifact and hand them the link**, then wait.

⭐ **This report is the FIRST of the only two artifacts the whole flow publishes** — the other is
the closing report of the last `/flx-verify` — and it is where the user approves the data model and
the screens **together**, because this is the moment there is something to approve. So it opens
with the model: the entities of step 3 as they stand after the corrections, which are master and
which transactional, the cardinalities, and the menu sections. The screens come after, each one
named by its key. Neither `/flx-plan` nor `/flx-discuss` nor any `/flx-execute` block publishes
another one on top of this.

What the report carries, per screen, and nothing else:

- **A key, short and visible, and it goes first** — `L-A`, `F-D`, `P-E`: one letter for the shape
  (list, record card, dashboard) and one for the entity or the variant. Every heading, every census
  and every question in the report names its screen by that key, because a 32-character Stitch
  `name` is not something a person can say out loud.
- **The screen itself, at full size.** Prefer the archived `.html` in an `iframe` — it is the real
  markup, it reads at any zoom, and with a switcher between screens they can walk the set like a
  prototype. The screenshot is the fallback, and it goes in at **`=s0`** size (see step 5); a 512 px
  image is unreadable and that is what a person is being asked to approve.
- **The census**, beside its screen: every field, label, widget, action and state the screen shows.
  That is what turns "here is a picture" into something a person can check, and it is the same
  census step 7 already demands of you.
- **What the design added on its own**, marked as such — a field the model does not have, a label
  nobody asked for, an action nobody requested.
- **The decisions you need**, numbered, each one a question they can answer in a line.
- **What you could NOT verify**, said plainly.

⛔ **What the report must NOT contain**: a comparison against any other product or vendor — nobody
is buying one — and any adjective about quality nobody can check ("close to the level of X",
"mature", "professional"). One run reported a design as approaching a competitor's
level, which is unverifiable, unasked for, and reads as a verdict when the verdict is the user's.
Describe what is ON the screen; the judgement is theirs.

**And the report closes with a block titled "If you do not approve something, say it by its key".**
Say there, in the user's own words, that the answer does not have to be all or nothing: **"in `P-A`
change X"** edits that one screen, **"redo `L-E` and `P-E`"** generates those two again, and anything
not named stays exactly as it is. Without that block the user has pictures and no handle on them,
and the only way to reject one screen is to reject the set.

And **read the HTML** where there is one: it is semantic, so the sections, the columns and the
fields come out. When all you have is images, read the images with the same care — what a screen
shows is what has to be reproduced either way.

**Take a census, not a glance.** List every field, label, widget and action the screen shows, one by
one, and check each against the request and the model from step 3. Anything the design added on its
own — a field the model does not have, a label the request never asked for, an action nobody
requested — goes to `/flx-discuss` before it is built, and the answer is recorded with
`flexygo_record_decision`. An invention that reaches the screen unasked is a review defect: of five
inventions in one screen only one was ever asked about.

- **They confirm** → record it with `flexygo_record_decision` and carry on.
- **They ask for changes** → they will have named the screens by key. `edit_screens` on **only** the
  screens they named, or a fresh generation for the ones they ask to redo; every screen they did not
  name is left untouched. ⚠️ **Pass `modelId` and `deviceType` to `edit_screens` too — the same
  ones §5 generated with.** It takes both; passing neither means an
  approved design generated on `GEMINI_3_8_FLASH` gets edited on whatever the week's default is.
  It is the defect §5 warns about, on the half of the flow nobody had looked at.
  ⛔ **And hash each edited screen before saying it changed** — §5 point 4. A user who asked for a
  change and is told it is done, over a file that did not move, finds out in step 7 at the earliest
  and after building at the latest. Then back to step 6 replacing the reference **for the ones that changed**:
  what gets compared is the agreed design, not a draft that was discarded. Say back which keys you
  touched and which you left alone before showing the set again.
- **They reject it** → stop. Do not build.

## 8 · Build

`/flx-plan`, `/flx-discuss` and `/flx-execute` block by block, as always.

⛔ **And the screen the modules will not give you.** Reading the HTML in step 7 is also where this
gets decided: a design asks for arrangements a list or a card does not paint — a summary band across
the top, three figures side by side, something that is not rows of records. Deciding it now is the
point; discovering it halfway through execution means a block that cannot be closed.

**That screen is `flexygo_create_html_module`**: your own HTML, CSS and JS, written against the
platform's own variables so it does not look like it came from another application —
`flexygo_get_catalog('css_variables')` for the tokens, `flexygo_get_html_controls_reference` for the controls
and their context tokens, `flexygo_get_js_reference` for navigating and running processes from it.

⚠️ **For the screen that does not fit, not for the ones that do.** A listing that a list module
already paints, rewritten by hand, is a screen nobody maintains and that stops following the skin
the day somebody changes it. The test is whether a module CAN do it, not whether HTML would be
quicker to write — and if the answer is that no module can, say so when the plan is written, not
when the block is half done.

The choice is not free-hand: `flexygo_get_custom_screens_reference` carries the ladder —typed module
as it comes, typed module with its own template and CSS, a SQL-driven module, free HTML in a
plugin— and what each rung costs in pager, search, presets and offline. **Read it before choosing**,
and write the chosen rung into the plan, per screen. That ladder is the same on the three roads of
step 0: it is decided by what the screen has to reproduce, not by who drew it.

**Seeding is not optional here.** An approved design comes full of sample data and a freshly built
Flexygo screen is empty: without seeding, the final comparison would come out "different" on every
row for the wrong reason.

⛔ **And that includes the photographs.** When the model carries an image property and the original
shows photos, the seeds have to answer for them: either the images are seeded, or you **ask the
user**. A silent placeholder is neither of those, and it was the single largest visual difference of
the first real pass — in a run whose own report never named it as a gap. The rule, and the
route for seeding images (files to the Frontend's `wwwroot`, web path into the column), is in
`flexygo_get_schema_and_seeding_guide`.

## 9 · Compare against what was agreed

`/flx-verify` checks that it works on screen. After that,
`flexygo_generate_design_comparison` says which rows to compare and
`flexygo_record_design_comparison` records the verdict. It does not accept "it looks similar": every
row is `same`, `similar`, `different` or `not-applicable`, and `not-applicable` requires a note.
Pass the count `flexygo_compare_design_measurements` just printed for this screen as `deviations`,
or a later pass has no number to subtract this one from.

⛔ **If a row turns out to have been judged wrong, or gets closed later, amend it — do not
re-measure the whole screen.** `flexygo_amend_design_row` corrects the `verdict`, `note`, `fix` or
`cause` of ONE already-recorded row and stacks a new entry with the other eleven copied as they
stood; `flexygo_record_design_comparison` is for a fresh pass, not for fixing one row of an old one.

⚠️ **And the twelve rows are ALL visual, so they cannot catch invented logic.** A copy identical
to the pixel whose rules were made up scores 11 `same` / 1 `similar` / 0 `different`. That is why
`flexygo_record_design_comparison` also requires `behaviours`: what this screen does that the screen
itself cannot show you — a control whose effect is not visible, a value whose rule is off screen, a
state the original can be in, a navigation with no destination built. Do NOT invent any of them: ask
the user whether they want a **placeholder** for now or would rather **explain** it, and record which
of the two was chosen. `[]` is a valid answer and is recorded as the claim it is.
⛔ **And if you find one you cannot settle by reading anything, do not drop it: declare it
`needs-user`.** That is the fourth resolution, and it is the state half of a real bank is actually
in — some of what a screen does cannot be worked out from any reference and only the user knows it.
It is not the cheap exit: it takes the `question` you are going to put to them, written out, and a
screen with one open is **not closed**, whatever the twelve rows said. The failure it
exists against is seven findings deleted for want of a box to put them in, and one screen signing
"None declared" over two its own report had left explicitly open.
`flexygo_get_custom_screens_reference` §15 has the triggers and three worked examples.

And `evidence`, one line per screen: WHICH reference, and over WHICH record or state of the data
the copy was measured. A record card compared over an empty record, or over a different one than the
approved capture shows, weakens every row at once — and without this field nothing records that it
did. On the generated-project road the `palette` row also has to carry a **colour** in its note: the
hex measured on the built screen and the token hex it was compared against. Without one the tool
refuses and hands back the original's tokens — the value is the list, not the refusal.
`flexygo_get_custom_screens_reference` §17.

Ten of the twelve rows have to come out **almost identical**; **typography** and **spacing** aim
lower only when the original is a PNG — an image has no `font-family` at all, and its pixel distances
are not comparable once the capture's render scale is unknown. Where the original's own SOURCE is on
disk that excuse does not exist and those two aim at almost identical like the rest, so read the
Target column of the script instead of assuming the low bar. And do
not judge it with a comparison of labels: during the trial run, a regular-expression detector passed
a screen that had a to-do list with ticked boxes, because they were drawn with `div` and not with
`input`.

⛔ **A row that does not come out `same` is closed or raised — never filed as taste.** The full
rule, with the classes of cause the note has to name, is in `/flx-verify`. The short form: "decision
of style" closes nothing.

Never write `.flexygo/` by hand. Never seed data without the user's explicit permission.

Whatever the design step ends in — confirmed, changed or rejected — say what state it left and **which command comes next**.

And when a unit of work closes, look at whether the SESSION should close with it: the
seams that are worth offering `/clear` on, and the three lines plus the ready-to-paste
prompt that have to go with the offer, are in `.claude/CLAUDE.md`,
under "Leaving the session". You cannot measure your own context — the seam is what you can see.
