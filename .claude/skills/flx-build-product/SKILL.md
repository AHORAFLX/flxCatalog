# Build a whole product

This is **not a separate flow**. It is the usual flow —`/flx-context`, `/flx-plan`, `/flx-discuss`,
`/flx-execute` block by block, `/flx-review`, `/flx-verify`, `/flx-test`, `/flx-quality`, `/flx-help`, and `/flx-api` when the
application is used from outside— with a plan wide enough to cover a
complete application. Do not write plan files yourself, do not classify the request into modes, and do not
split the work into batches of subagents: the tools and the MCP's requirements already do that.

What this skill adds is the **ambition**: which blocks are needed for what gets built to be a usable
application and not a pile of tables.

## Before anything else · Gather the available sources

At the start of a product built from scratch, first ask the user for **all information sources they
can provide** before discussing the model, design or plan. Ask them to place the files in a
`Resources/` folder at the project root; create that folder if it does not exist. Include anything
potentially useful: requirements, business rules, existing process descriptions, sample data,
spreadsheets, database schemas, API documentation, reports, screenshots, reference applications,
branding and constraints. For material that cannot be copied locally, ask them to put its URL and
relevant context in a text or Markdown file inside `Resources/`.

Once the user says the folder is ready, inventory and review its contents, then summarize what is
available and note important gaps. Do not start design, modeling or planning until this review is
done. If the user has no sources, ask them to confirm that and continue with the existing flow; do
not make the request a dead end. Then proceed to the approved-design question below.

## 0 · Is there an approved design already?

**After reviewing the available sources, ask this before anything else.** Many people arrive here —
"I want an application for…"— carrying screens **the client has already approved**. If that is
the case, this is not designed: it is
implanted, and the work is judged by comparing it against that original.

**Ask it as ONE question, not as a menu**, because the two things that matter are the same thing:

> «Do you have a project or reference images to work from? If you do, tell me the path — the
> generated project's folder, or the folder with the screens.»

⛔ **And ask for the PATH in the same breath.** A "yes" with nowhere to look is not an answer: the
work cannot start until the files are on this machine. If they have a generated project somewhere
else — still in the generator, in a zip, in a drive — say so plainly: **they download it first, and
we carry on when it is on disk.**

What the answer opens:

| What the user brings | Where to go |
|---|---|
| A folder generated by Lovable or another generator | `/flx-lovable` with the path — it also reads the model and the design tokens out of the code |
| **Their own screens**: screenshots, an HTML, a PDF, a link to a demo already approved | `/flx-design`, telling it those screens are the original |
| Nothing | `/flx-design`, which draws them with Google Stitch — see below when Stitch is not set up |

These roads are **all first class**. What governs the work is that there IS an original, never which
road it came by.

⛔ **The screenshots road is not a fallback.** It is how most approved designs actually arrive — a
demo was shown, the client said yes, and what survives is a folder of PNGs. An agent that receives
one is on a sanctioned path, not improvising: the screens get filed with `flexygo_record_reference`
exactly as on the other two roads, and from there the palette taken off the screen, the technique
chosen per screen and the row-by-row comparison are identical.

If they bring a generated project, carry on inside `/flx-lovable`. Coming back here afterwards does
not work — the approved screens have to be filed before building, while the generated project is
still up, and if you do not there will be nothing to compare against at the end.

**If there is no original, OFFER TO MAKE ONE before carrying on.**

⛔ This is the difference between an application invented screen by screen and one built against a
shape somebody agreed to. `/flx-design` proposes the model, asks Google Stitch for the screens and
shows them **before anything is built** — and it files them as the *before*, so at the end there is
something to compare against instead of an opinion.

Offer it; do not impose it. Some people want to see it and some want it standing today:

> «There is no design to work from. I can propose the model and get some screens drawn so you see
> how it will look before I build it — that is `/flx-design`, and it takes a few minutes. Or I go
> straight to building. Which do you prefer?»

### When Stitch does not answer

⛔ **Do not answer this by asking for their screens again.** They are on the Stitch road precisely
because they already said they have none, and asking a second time is a loop that ends in "then we
stop". Find out WHICH of the two cases it is, because they have different answers:

- **Stitch is wired but has no key.** The project template already writes it into `.mcp.json`, so
  the tools are present. What is missing is one thing and it is small: Stitch authenticates with an
  **API key** in the `X-Goog-Api-Key` header, and the template leaves the placeholder
  `${STITCH_API_KEY}` there.

  ⛔ **And the failure mode is the one worth telling them about**: with the variable unset, the
  client's indicator goes **green** and the call fails with
  `Incompatible auth server: does not support dynamic client registration`, **at once**. Re-measured
  2026-09-03 on a clean bench: this paragraph used to promise a "401 about three minutes later" and
  to teach that a slow Stitch is a keyless one — wrong on the timing and wrong on the message. The
  green indicator is real and now explained: `initialize` and `tools/list` answer **200 with no
  credential**, so authentication is only ever exercised on a `tools/call`. "Stitch is configured"
  is still not something to conclude from the client looking healthy — but it is an immediate
  OAuth-shaped error that says so, not a long wait.

  **Walk them through it instead of telling them to sort it out**: the key is generated in Stitch's
  own Settings, starts with `AQ.` and never expires; it goes in the `X-Goog-Api-Key` header, and
  afterwards **the window has to be reloaded** (`Ctrl+Shift+P` → *Developer: Reload Window*) — a new
  chat is NOT enough, because the MCP servers are started once per window and a new chat reuses
  them. ⛔ **Until that reload the call fails with the SAME sentence it gave with no key at all**,
  so a retry straight after pasting the key looks like a bad key and is not one. `/flx-design` carries the full recipe — the exact
  `claude mcp add` line and its two traps, why a classic `AIzaSy…` key answers 401, and why the
  OAuth Stitch advertises cannot be used from the client. Send them there rather than improvising
  it. (`"timeout": 600000` in that entry is not optional either: without it the client gives up on a
  generation that was going to succeed.)
- **Stitch has its key and still does not answer.** Then it is down or slow. Say so and offer the
  fourth road below, or waiting.

### The fourth road: no original at all

**When there is no project, no screens, and no Stitch, there is still a way to build — and it is not
"build blind".** What replaces the original is not another picture: it is an agreed brief plus the
platform's own look, wearing the client's brand.

1. Agree the brief in conversation and record it with `flexygo_write_design_brief`: what the
   application is, its screens by name, the client's palette.
2. Put the brand on the skin — the seven variables `flexygo_get_module_styling_reference` names.
   That is what stops it looking like a stock install.
3. **Lead with the platform's own modules, and reach for `flexygo_create_html_module` where they
   genuinely fall short** — a summary band, three figures side by side, a layout that is not rows of
   records. It earns its place here exactly as on the other roads: what changes without an original
   is not whether HTML is allowed, it is **what disciplines it**. On the other three roads a screen
   is answerable to the picture; here it is answerable to the brief, so **what the hand-made screen
   is for goes into the brief and gets agreed before it is built**. What is off the table is using
   HTML to invent a whole design screen by screen with nothing to hold it to — which is the thing
   this gate exists to prevent, and it is a different thing from writing the module a screen needs.
4. Record the development as having **no original**. ⛔ **The row-by-row comparison is then not run at
   all** — there is nothing to compare against, and answering thirteen rows about a picture nobody drew
   is theatre. What replaces it is the part that still means something: checking the screens look
   right, and `flexygo_generate_interface_test_plan` to click through them, fill them and prove they
   work.

Say what that buys and what it costs, in one line, so it is a decision and not a default: **the
application will look like Flexygo with their brand on it, and nobody will pretend there was a
design to match.** Plenty of internal applications want exactly that.

⛔ **And when the design shows something the modules do not do.** A Flexygo module paints what its
template paints, and a designed screen will ask for arrangements no list or card gives you: a
summary band across the top, three figures side by side, a layout that is not rows of records.
**That is what `flexygo_create_html_module` is for** — HTML, CSS and JS of your own, with the
platform's own CSS variables so it does not look like it came from somewhere else
(`flexygo_get_catalog('css_variables')`, `flexygo_get_html_controls_reference`, `flexygo_get_js_reference`).

Use it for the screen that does not fit, not for the ones that do: a list that a list module already
paints, rewritten by hand, is a screen nobody can maintain and that stops following the skin. The
test is whether a module can do it, not whether HTML would be quicker to write.


## 1 · Context

If the project has no context recorded, `/flx-context` with what you know of the domain, the
three-letter prefix and the client's own conventions. Without this the plan comes out with no prefix
and no judgement.

## 2 · Load the references before planning

The model knows SQL; **it does not know Flexygo**. Before proposing anything, call:

- `flexygo_get_conventions` — naming, master tables, normalisation, soft-delete, filters.
- `flexygo_get_entity_anatomy` — what parts an entity is made of and in what order they are built.
- `flexygo_get_schema_and_seeding_guide` — creation order and the rules of seeding.
- `flexygo_get_property_type_guide` — which property type each column takes.
- `flexygo_get_process_and_dependency_guide` — what each entity needs beyond CRUD.
- `flexygo_get_dotnet_process_guide` — only if some process carries C#: the contract the platform
  invokes your method with, and the recipes (PDF report, email with attachment, WebAPI).
- `flexygo_get_reports_reference` — the moment a record needs a PDF, or an email needs one
  attached: that is a REPORT (`flexygo_create_report`), never a process drawing bytes by hand. Who
  renders each of the seven `Reports_Types`, why a record's download needs no process at all (the
  toolbar's `Print` button), and the real security gate — `Security_Reports_Roles`/`Users`, not
  `Objects.CanPrint`.
- `flexygo_get_notifications_reference` — when a record has to email someone or raise an in-app
  notice on its own: one `Notices_Sentences` row a system job reads every 5 minutes, the exact
  columns each sentence must output, the recipients rule, and the Update sentence without which the
  same rows are sent again and again.

And before building the visible layer, when the time comes:

- `flexygo_get_module_composition_guide` — modules, related lists, layouts and the kanban.
- `flexygo_get_dashboard_reference` — only if the approved original shows a dashboard, or the user
  commissioned one in `/flx-discuss`: the dashboard recipe, the EasyInfo KPI columns and the chart
  contracts; a right query still draws a wrong picture and only the screen shows it.
- `flexygo_get_module_styling_reference` — the four levels of styling, the two themes and how to
  check a plugin actually loaded.
- `flexygo_get_date_modules_reference` — only if the product carries a timeline, a calendar or a
  planner: the three are not interchangeable, and almost nothing they get wrong fails loudly.
- `flexygo_get_template_syntax_reference` — formatters, `flx-navbutton`, grid and classes.
- `flexygo_get_html_controls_reference` — form controls, context tokens, validators.
- `flexygo_get_js_reference` — the client API, for any `onclick` or clickable KPI.
- `flexygo_get_custom_screens_reference` — only if a screen has to MATCH an approved original
  (Stitch, a generator, or the user's own screenshots): the ladder from a typed module to free
  HTML, how a hand-written block saves, and the two things `flx-html` cannot do.
- `flexygo_get_offline_apps_reference` — only if the product carries a mobile app: none of the above
  applies there — the screens are Ionic, the objects are clones, and the installation has to enable
  the WebAPI and restart before the device sees a single row.
- `flexygo_get_offline_screen_components_reference` — before writing a single mobile screen: which
  components the device carries and which attributes they really accept, which are not the online
  ones. What gets written with the wrong names does not fail, it comes out blank. It also says how
  to tell which shell the phones run, and carries the recipes for the new 2026 one — used only on
  that shell, and only when the project has no design of its own.
- `flexygo_get_offline_js_reference` — before writing a line of JavaScript for the device:
  `window.flexygo` there is not the web object of the same name, and the `jsAfterLoad` hook holds
  500 characters, is a synchronous eval and runs on every render, not once.
- `flexygo_get_app_shell_reference` — before touching the frame around the application: the side
  panel, the top bar, the logo and the global CSS/JS are five columns of one `dbo.Interfaces` row,
  each one switching its widget off when left empty. Read it before deciding the navigation chrome
  cannot be changed, and before assuming the interface flagged `IsDefault` is the one that paints.
  It also carries the **guest mode**, which is asked for as "a public screen" or "what someone sees
  before signing in" and is neither a role nor something to build: every installation already ships
  a `webguest` interface and a `Not Registered` role. Tying a page to it with `interfaceName` is
  only a preference — the resolver falls back to any page of the object ignoring that column — so
  `flexygo_set_page_security` is what actually keeps the page for the guest and off everybody
  else's screen.
- `flexygo_get_security_reference` — **before planning, whenever `/flx-context` recorded several
  roles or public screens** (the plan carries their block, B-6 below), before writing a single
  permission, and before promising a
  customer that a role "will not see" something: a row is written to take away, absence means
  permitted, and for the guest role that rule is inverted — it starts from everything denied, so
  a public screen has to be granted at FOUR levels — the page, every module on it, the object
  behind each data module, and every property those modules show — and missing one comes up
  half-built with no error anywhere. It also says which surfaces are written and never read,
  and what a filter may contain.
- `flexygo_get_webapi_reference` — whenever anything reads this project from OUTSIDE it: a phone, a
  customer's system, or you checking your own work through the REST surface. Nothing there is open
  by default and nothing refuses in a way that looks like a refusal — the caller gate answers `401`
  in the exact words of a wrong password, and the object gate answers `Unauthorized collection`:
  as **HTTP 200** in the `Ajax` envelope from a Frontend before beta.83, as `401` or `403` from a
  later one. It also holds which of the two `/token` endpoints is the real one,
  which is where a walk lost six probes.
- `flexygo_get_erp_integration_reference` — only when the data model belongs to the customer, and
  then before the first block: the schema travels as deployment scripts because publishing the data
  project over their database overwrites what is already there, the login has to hang an ERP session
  on the connection or every statement travels without one, five column names are filled by the
  platform itself, and the conventions have to be broken on purpose. Nothing on that road fails
  loudly, so it is read up front or diagnosed weeks later.
- `flexygo_get_additional_tables_reference` — the moment an object's data turns out to live in more
  than one table, which is the ERP shape: the standard table plus a parallel one holding the
  customer's own fields. Adding a field there already works with the tools that exist —  the
  platform deduces a property's table from where the column lives — so read it before going looking
  for a tool that is not there, and before touching rows that already exist: the list still paints
  a record with no matching row (the platform's filter is a LEFT JOIN), but opening that record
  fails until the row exists — the acknowledgement of `flexygo_add_additional_table` carries the
  INSERT that fixes it.
- `flexygo_get_help_reference` — once quality has swept a screen: its guided tour, the help of its
  fields and its page of the application's help, with screenshots on the demo data, for whoever uses it.
- `flexygo_get_testing_reference` — once the processes and screens are verified: the product's own
  UnitTest and InterfaceTest, what the template ships broken, and a test per new process and screen
  that creates its own data, goes red once on purpose, and runs in CI before every publication.
- `flexygo_get_quality_reference` — after the block is verified, and before telling anyone it is
  done: the closed catalogue of fourteen things a copied screen is missing, each with the read that
  detects it and the mechanism that fixes it. A 100% faithful copy can still be a bad application,
  and no earlier gate can see an absence nobody wrote.

Introspect the project as well: `flexygo_get_objects`, properties, navigation and tables. A new
product almost never lands on a virgin database.

⛔ **And when the model is the customer's (an ERP — `/flx-context` asked it), NEVER ask
`FlexygoShowSchema` for `*`.** An ERP is hundreds of tables and `*` returns every one of them: it
eats the whole context in a single call, and **leaving `tableName` empty means exactly the same
thing** — the tool defaults it to `*`. Name the tables that matter, comma-separated. One table comes
back **with the ones its foreign keys reach**, which is how you see what it hangs off without asking
for the database. Alongside it, `flexygo_execute_query` reads rows (500 at most, and the
configuration database is refused) and `flexygo_propose_properties_from_table` derives the
properties from the real columns — required from nullability, hidden from identity, the type from
the SQL type.

## 3 · Plan in blocks, with `flexygo_write_plan`

A whole product needs, at minimum, these blocks. Adjust the number to the domain, but do not melt
them into one: `/flx-execute` checks block by block, and that is what stops you building on nothing.

| Block | Contents |
|---|---|
| **B-1 · Schema** | Tables in order master → parents → children — but when the data model is not ours, read the fork below first: nothing is created in that database directly |
| **B-2 · Entities** | Objects (one at a time), properties, list views, filters, record view, pages |
| **B-3 · Relations and logic** | Relations last; then processes; then dependencies |
| **B-4 · Modules and pages** | List and record modules, related lists and composition follow what the approved original shows, screen by screen; a document and image manager where the original shows one — an upload, a gallery, an attachments panel, on a screen or in the generated code; document or image properties the original does not show are a §4 question, never a silent build |
| **B-5 · Navigation and startup** | Menu and startup page, wired to the navigation the approved original shows; a dashboard only if the original shows one — or the user commissioned it in `/flx-discuss` (extend the original first with `/flx-design` when possible) |
| **B-6 · Who sees what** | When `/flx-context` recorded several roles or screens that open without signing in: roles and profiles first, then the security of objects, pages, modules, navigation and processes, each task saying what every role sees and does, by the names the project memory carries. `flexygo_write_plan` refuses a building plan without it, unless the user decided that every role sees everything (`securityWaivedBy`) |
| **B-7 · Demo data** | Always the LAST block, behind every process and screen: one task that names `flexygo_demo_data` and says which states of each screen it covers, dates counted from today and the `DEMO` marker. `flexygo_write_plan` refuses a plan with screens without it, unless the user decided to go without demo data (`demoDataWaivedBy`) |

The blocks are the **order** — platform truth, and what `/flx-execute` checks block by block. The
**approved original is the list**. Only when there is no original at all (§0, the user declined to
draw one) do this table's contents stand as the house proposal, and even then they go through
`/flx-discuss` as a proposal, not imposed.

### B-1 forks on who the data model belongs to

⛔ **Read back what `/flx-context` recorded before planning B-1: is the main data model ours, or does
it belong to a system that was already there — an ERP, the customer's own database?** It changes the
whole block, it is not inferable, and nothing downstream complains when it is got wrong. If it was
never recorded, ask it now and record it before writing a line of DDL.

- **Ours** — B-1 exactly as the table says: `flexygo_execute_ddl` against `DataConnectionString`,
  `flexygo_script_data_structure` to take the model into the data project, and SSDT publishes it.
- **The customer's** — ⛔ **nothing is created in that database directly. Nothing at all**: not a
  table of ours, not a column on one of theirs, not an index, not a row of seed data.
  `flexygo_execute_ddl` and `flexygo_execute_dml` are off the table for the whole build. Everything
  goes through `flexygo_register_deployment_script`, which leaves the SQL waiting and runs nothing
  now: the application executes it when it starts and marks it as done — **the only route that runs
  itself on every installation**, instead of living in the database you happen to point at. That is
  how the platform's own products ship theirs.
  ⛔ **`flexygo_execute_ddl` and `flexygo_execute_dml` refuse an ERP database on their own**, a
  hard refusal that does not depend on the agent remembering to withhold it — **with one toll, not
  an exception**: a statement whose every touched object carries the prefix the project declared in
  `/flx-context` (`Pers_` for one customer's implementation, the product's own — `FRUTI_` — for a
  product sold to several, which never writes with `Pers_`; at the start of the name or after a first
  word, as in `vPers_`; reads may name any ERP table), or that only adds, changes or drops columns
  carrying it in one of the ERP's own `Conf_` tables, runs, during development, and its acknowledgement says where the result
  has to end up: through `flexygo_register_deployment_script`, idempotent, like everything else in
  this block. For anything else the user wants created on that database directly, the route is
  theirs to take, not this server's: start the application and let its own script jobs create it,
  then work with what they created.
  Whoever starts it stops it — see `/flx-verify`, "Whoever starts it stops it": measure the port
  before starting, stop what you started when the phase ends, and say what was left running.

  Four things the block has to get right:
  - **Every script carries its idempotence guard**, naming the object it creates
    (`IF NOT EXISTS (SELECT 1 FROM sys.tables WHERE name='...')`, or
    `IF COL_LENGTH('dbo....','...') IS NULL` for a column), or the registration is refused. A script
    that fails half-way is picked up again on **every** boot, forever.
  - **`executeOrder` is the order**, not the script id: lower runs first, which is how a script gets
    the table another one creates.
  - **`flexygo_list_deployment_scripts` after the first startup**, always. It says pending, done, or
    failed with the error the application recorded — and that error sits in a column nobody looks at.
    A wrong or failing one is removed with `flexygo_delete_deployment_script`; one that already ran
    (state 'S') is refused, because the row is the record that it ran.
  - **The plan says so**: B-1's tasks are "register script X", not "create table X", and the
    assumption that the customer's database has the tables we hang off carries its `affects`.
  - ⛔ **And before the first row is written to one of THEIR tables, two silent things.** The
    platform fills some columns by itself decided by the column NAME (`Usuario`,
    `FechaInsertUpdate`, `InsertUpdate`, `IdDoc`, `OriginId`), and the table may already have its
    own write API — a `p{Table}_I` stored procedure that an object created here would bypass.
    Check both with `flexygo_get_erp_integration_reference` §5 and `flexygo_get_settings`. Neither
    fails when it is got wrong: the row saves and the wrong thing happens.

⚠️ **The rest of the product does not change.** B-2 to B-5 are built the same way on top of the
ERP's tables: objects, properties, modules, pages and navigation know nothing about how the schema
got there.

⚠️ **And the seeding question of §4 is about OUR tables.** Rows in a system that is already running
are the customer's data, not test data — nothing is seeded, migrated or deleted there without them
saying so, in those words.

Rules when writing the plan:

- ⛔ **The plan ends there. Do not add a verification block, nor a review one**, however natural it
  looks to close a whole product with one. `flexygo_write_plan` refuses it, and the refusal names
  the reason: measured three times, a plan ending in a block called «Verification» got its three
  tasks ticked with `record_execution`, the run announced everything verified, and
  `verifications.md` was left empty — no browser, no screenshot, no verdict. Once verification is a
  row in the plan it is executed like any other task, and the phase that opens the application and
  can send tasks back to pending is never reached. What is built goes in the plan; the phases run
  between plans, and each has its own command.
- Mark `parallel: true` only where there really is no dependency. Objects **never** go in parallel:
  the `Objects_ITrig` trigger causes deadlocks.
- Every assumption carries `affects`. In a whole product the assumptions are many, cheap to write
  and very expensive not to revise.
- Anything depending on a user decision —the MVP's scope, which entities are operational and which
  are master, whether data is seeded— goes as `clarify` on its task, not as a supposition.

## 4 · Discuss before building

`/flx-discuss` walks the open points. In a whole product the most expensive one is usually the
scope: ask what goes into the first version before planning fifty tasks nobody asked for.

**Four decisions to get out of the user before touching the schema.** They are not matters of
opinion and they do not follow from the brief; building without them is expensive because they get
discovered halfway:

| What to ask | Why it cannot be assumed |
|---|---|
| **Category of the data**: master, transactional or a mix? | It decides the whole creation order and what carries history |
| **Are the master tables** you propose created, and which? | Show them the concrete list. One master too many is a screen nobody uses; one too few is a free-text field where there should be a dropdown |
| **What does the demo data show** — or does this go without it? | Without data there is no way to look at whether a list works. Ask which states each screen has to show, and name the target database: it is seeded there, and nowhere else. Going without is the user's decision, recorded and cited as `demoDataWaivedBy` |
| **Is any entity missing?** | It is the question that pulls out the most entities, and the only open one of the four |

**Two more decisions belong here too, before the visible layer (B-4/B-5) gets built** — later than
the first four because they need the shape of the visible layer, but no less to be got out of the
user rather than assumed:

| What to ask | Why it cannot be assumed |
|---|---|
| **Which screen opens the app** — and is there a dashboard? | If the original shows a home, that is the startup page, built as shown. If it shows none, the user picks one of its screens — and a dashboard the original does not show is drawn first (`/flx-design`) or recorded as an out-of-original commission, never fabricated silently |
| **Do any entities carry attached documents or photos**, and which? | The original can be silent while the domain is not — an upload lives behind a button no screenshot captures. A manager nobody asked for is a screen nobody uses; one that is missing turns up at handover. Two sanctioned outs, and silence is neither (sibling doctrine to the photos rule in the seeding guide) |

Every answer goes to `flexygo_record_decision` with its `affects`. **Unrecorded does not count**: the
decision is taken once and consulted for days, and one that exists only in the conversation is lost
the moment the session is cut.

Ask, and record, in the user's language.

> This used to be a form-based confirmation tool, retired on 20-ago: elicitation is a request from
> the server to the client, it disappears under protocol `2026-07-28`, and with `--http` —which runs
> stateless— the form never reaches a human. The questions were good; the channel was the wrong one.
> Asked here they work on any transport, and they also stay written down, which that tool did not do
> either.

## 5 · Execute block by block

`/flx-execute B-1`, and when the user asks, `B-2`. Do not chain blocks on your own initiative:
between one and the next is when it shows that something came out different from what was planned.

On closing each block, say in one line what got built and which is next — in the terminal. The
whole flow publishes **two artifacts**: the model with its screens when it is decided (§0's
`/flx-design`, or `/flx-discuss` when there was no design) and the closing report of the last
`/flx-verify`, which `/flx-quality` extends. A block is neither.

## 6 · Review

`/flx-review` checks what was agreed against what was built and records every deviation with
`flexygo_record_review`. A product that passes `flexygo_verify_object` can still have lists that
return no rows and record cards with no navigation button: the review catches that, not the
verification.

## 7 · Verify on screen

`/flx-verify` is the last step and the only one that looks at what a person will actually see: it
opens the pages in a browser, takes the screenshot, contrasts it against the minimums and records
the verdict with `flexygo_record_verification` — a verdict that can send a task back to pending.

**A whole product is not finished when the last block closes.** Every block ticked, every object
answering `flexygo_verify_object` and a review with no deviations still say nothing about an empty
list, a template painting a quoted CSS class, or a dashboard whose modules land on top of each
other. Say it to the user in those words: what is built is one thing, and what is seen is another.

## 8 · Then leave the tests in the product

`/flx-test` comes next: a unit test per new process and an interface walk per new screen, written
in the product's own UnitTest and InterfaceTest, seen red once on purpose, and run green by
`flexygo_run_tests`, which records the run itself. A product without them is verified today and
unguarded tomorrow; the CI runs the unit tests before every publication.

## 9 · Then ask what it is MISSING

`/flx-quality`, block by block, comes after the tests. It reads
`flexygo_get_quality_reference` and walks the block's modules against a closed catalogue of fourteen
absences — no pager, no empty state, no way back, no security row — and records each one with
`flexygo_record_quality_finding`, anchored to the module or the page and never to a task.

**Nothing is fixed there on initiative.** The findings go to the user with what each one costs
them, and what they decide is what gets recorded and built.

## 10 · Then the help, for whoever uses it

`/flx-help` comes after quality: each screen built gets its guided tour, the help of the fields that
need it, and its page of the application's help by task, with screenshots taken on the demo data and a
button on the screen that opens it. The server checks the three before it records each one. A product nobody can learn without
asking is not finished.

## 11 · And, if it is used from outside, what goes out

When `/flx-context` recorded that someone uses the application from outside — an AI assistant,
another system — the flow does not end at the help: `/flx-api` is the last step. It
proposes what of the built goes out over the WebAPI, read only by default, and for which roles; the
user decides; it is written, probed from outside with one user per role, and recorded with
`flexygo_record_exposure`. Until that is recorded, the development is not complete.

Never write `.flexygo/` by hand and never run SQL outside the MCP tools.
Never generate or migrate data without the user's explicit permission.

At the end of every block, say what got built and **which command comes next**.

And when a unit of work closes, look at whether the SESSION should close with it: the
seams that are worth offering `/clear` on, and the three lines plus the ready-to-paste
prompt that have to go with the offer, are in `.claude/CLAUDE.md`,
under "Leaving the session". You cannot measure your own context — the seam is what you can see.
